# stoke cache-server -- STOKE_REMOTE_CACHE_URL 레퍼런스 서버

- 날짜: 2026-09-20
- 종류: feat

## 배경

`STOKE_REMOTE_CACHE_URL`(HTTP 원격 캐시) 작업 때 "stoke는 클라이언트만 제공하고 서버 구현체는 안 준다"로 남겨뒀던 부분. 사용자가 실제로 캐시 서버를 쓰려면 프로토콜(`GET`/`PUT /objects/<key>`, `/dirs/<key>.tar`)에 맞는 서버를 직접 짜야 했는데, 이 진입장벽을 없애기로 함.

## 뭘 저장하는지 (사용자 질문 정리)

캐시 서버가 들고 있는 건 컴파일 결과물뿐임 -- 소스만 있으면 언제든 다시 만들 수 있는 파생물이라 DB나 정합성 보장 없이 "있으면 쓰고 없으면 미스" 수준이면 충분함:
- C/C++ 컴파일된 `.o` 파일 + 헤더 의존성 매니페스트(JSON) -- 키는 "소스 내용 해시 + 컴파일러 + 플래그"로 만든 지문
- Java 컴파일된 클래스 디렉토리 전체(tar로 묶어서) -- `javac`가 타겟 전체를 한 번에 배치 컴파일해서 파일 1:1 매핑이 없기 때문

원리는 "같은 입력 → 같은 출력"이 보장되는 컴파일의 특성을 이용해서, 한 머신이 컴파일해둔 결과를 다른 머신/CI가 재사용하는 것.

## 변경 (1차 구현)

`src/stoke/cache_server.py` 신규:
- `http.server.BaseHTTPRequestHandler` 기반, `GET`/`PUT`만 지원하는 최소 구현. DB 없이 파일시스템에 그대로 저장.
- 경로는 `objects/`, `dirs/` 프리픽스만 허용(그 외는 400) + 캐시 루트 밖으로 못 나가게 resolve() 검증(zip-slip류 방지).
- 선택적 HTTP Basic Auth (`--user`/`--password`) -- 클라이언트의 `STOKE_REMOTE_CACHE_USER`/`PASSWORD`와 대응.
- `ThreadingMixIn` 기반이라 여러 클라이언트(팀원/여러 CI 러너)가 동시에 접속해도 됨.
- 업로드는 임시 파일에 먼저 쓰고 rename으로 원자적 교체 (기존 `remote_cache.py`의 디렉토리 백엔드와 같은 패턴).

## 보안 하드닝 (2차, 사용자 질문 계기)

1차 구현 직후 "저 서버는 털려도 상관없는 거냐"는 질문을 받고 실제로 취약점 점검: 인증이 선택사항이라 기본으로 완전히 열려있었고, 무엇보다 **캐시 포이즈닝**이 가능했음 -- 서버는 특정 지문에 올라온 바이트가 진짜 그 소스를 컴파일한 결과인지 검증할 방법이 없어서(소스 자체를 안 갖고 있으니까), 쓰기 권한이 있는 공격자가 악성 컴파일 결과물을 특정 지문으로 심어두면 팀원/CI가 그대로 받아쓰게 됨. `stoke audit`/SBOM/provenance로 막으려던 것과 같은 종류의 공급망 문제를 이 서버가 새로 만드는 셈이라 바로 고침:

- **인증 필수화**: `--user`/`--password` 없으면 서버 시작 자체를 거부 (CLI 레벨에서 막음, 서버 로직까지 안 가고 바로 종료).
- **기본 바인딩을 `127.0.0.1`로 변경**: 기존엔 `0.0.0.0`이 기본값이라 실수로 전체 네트워크에 노출될 수 있었음. 이제 명시적으로 `--host 0.0.0.0`을 줘야만 넓게 열림.
- **write-once**: 이미 있는 키에 `PUT`하면 `409`로 거부(파일 존재 여부를 쓰기 직전에 한 번 더 확인해서 동시 요청 경합도 방지). 정상 캐시 항목이 나중에 악성으로 바꿔치기되는 걸 막는 최소 방어선 -- 완전한 해결책은 아니지만(첫 번째로 심는 공격 자체는 못 막음), 인증 필수와 결합하면 "신뢰된 사람만 쓸 수 있고 한 번 심긴 건 못 바꾼다"가 됨.
- **업로드 크기 제한** (`--max-upload-mb`, 기본 200): `Content-Length`가 넘으면 `413`, 디스크 채우기 DoS 방지.
- **TLS 내장 지원** (`--cert`/`--key`): `ssl.SSLContext`로 서버 소켓을 감싸서 별도 리버스 프록시 없이 HTTPS 직접 서빙. 안 주고 localhost 아닌 주소로 바인딩하면 "평문으로 오간다"는 경고 출력.

`stoke cache-server --user X --password Y [--port] [--dir] [--host] [--cert] [--key] [--max-upload-mb]` 서브커맨드로 등록 (auth 관련 필수 인자 검증은 `cli/cache_server.py`에서).

## 검증

**1차(기능)**: 실제로 서버를 띄우고, 실제 C 프로젝트 빌드를 그 서버를 거쳐서 두 번 돌려봄:
1. **인증**: 인증 정보 없이 GET → 401, 올바른 Basic Auth로 GET(캐시 미스 상태) → 404 확인.
2. **첫 빌드**: `STOKE_REMOTE_CACHE_URL`을 이 서버로 설정하고 `stoke build --force` → 서버 저장 디렉토리에 실제 `.o` 파일 + `.headers.json`이 생기는 것 확인.
3. **캐시 히트**: 로컬 빌드 상태(`.stoke/`)를 완전히 지우고 다시 빌드 → **"remote cache hit src/main.c"** 로그로 실제로 서버에서 받아와서 재컴파일을 스킵한 것 확인.

**2차(보안 하드닝)**: 전부 실제로 공격 시도하듯 테스트:
- `--user`/`--password` 없이 실행 → 즉시 거부(exit 1) 확인.
- 같은 키에 두 번째 `PUT`(다른 내용으로) → `409`, `GET`으로 원본 내용이 그대로인 것 확인(바꿔치기 안 됨).
- 1MB 제한 걸어두고 2MB 파일 업로드 → `413`.
- 인증 없이 `PUT` 시도 → `401`.
- `curl --path-as-is`로 `../../../../etc/passwd` 경로 탈출 시도(curl 자체의 경로 정규화를 우회해서) → `404`, 실제 `/etc/passwd` 내용이 새어나가지 않는 것 확인.
- 자체 서명 인증서(`openssl req -x509`)로 `--cert`/`--key` 지정 → 실제 HTTPS `PUT`/`GET` 왕복 성공, 같은 포트로 평문 HTTP 시도하면 연결 자체가 실패(TLS 소켓이라 평문 요청을 못 알아들음)하는 것 확인.

## 적용 안 한 것

- 캐시 용량 제한/오래된 항목 자동 삭제(eviction) -- 지금은 무한정 쌓임. 필요해지면 다음 단계.
- 캐시 포이즈닝의 근본 해결(서버가 컴파일 결과 자체의 진위를 검증) -- 서버가 소스/컴파일러를 갖고 있지 않은 이상 구조적으로 불가능. write-once + 인증 필수가 실질적 완화책.
- 멀티 서버/샤딩 등 고가용성 -- 단일 프로세스, 단일 디렉토리 기준의 가장 단순한 구현.
